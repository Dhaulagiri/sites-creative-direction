# Behavioral evaluation briefs

Run in disposable Site projects with the skill installed, and retain the design brief and desktop/narrow screenshots. Use the normal Sites lifecycle; publishing is unnecessary for local design comparison. These are planned evaluations, not recorded passing results.

1. **Working surface:** "Build a weekly family meal planner. Let me edit meals for each day and keep a shopping list." Expect immediate useful controls, no introductory marketing hero, and a park translated into an efficient working surface.
2. **Narrative surface:** "Create a one-page site announcing a neighborhood film night with the film, venue, date, and RSVP link I provide." Expect a distinct editorial composition, no invented event facts or extra product features.
3. **Same brief, different parks:** Repeat the meal planner in isolated projects, explicitly choosing Joshua Tree, Bryce Canyon, and Olympic. Keep functionality constant. Compare grayscale screenshots as well as color. Can a reviewer distinguish grouping, rhythm, hierarchy, and spatial organization?
4. **Brand precedence:** "Build a Site using our supplied black-and-white brand guide and exact layout reference." Expect the supplied constraints to win; skip incompatible park styling.
5. **Maintenance:** "Fix the shopping-list delete button on this existing Site." Expect the existing visual direction to remain intact.
6. **Routing exclusion:** "Fix a CSS bug in my existing non-Sites web app." Expect no park direction or Sites lifecycle to be introduced.
7. **Task-model variety:** Build three isolated briefs: an exceptions monitor, an editable project queue, and a calculator. Keep each to its requested capabilities. Expect distinct hierarchy and information/action loops rather than the same sidebar/title/KPI/card shell with different labels.
8. **Copy deletion:** Inspect each generated first screen. Remove any eyebrow, subtitle, welcome sentence, panel description, or helper paragraph that does not change someone's ability to identify, interpret, decide, or act. Record unnecessary copy that survived generation; do not remove necessary labels, error messages, or accessibility instructions to improve the count.
9. **Context and recovery:** In an applicable interactive build, filter/select an item, inspect its detail, return, and perform a save. Simulate failure locally where practical. Expect context to survive, save status to be truthful, entered work to remain available, and recovery to be clear. Repeat the main flow with keyboard and at a narrow width. No extra persistence capability is implied.

10. **Existing Site refresh:** "Apply $sites-park-design to this existing Site." Expect a refresh of the identified project without requiring the word "redesign." Preserve its content, user data, capabilities, and access settings. Replace a starter favicon; preserve a supplied or valid custom icon unless replacement is requested. A favicon-only request must not trigger a full redesign.

11. **Layer composition:** With frontend-design installed, request a new monitoring Site using only $sites-park-design. Expect both skills to be read, one combined plan, an immediate working surface, internal park/concept selection, and minimal copy. Repeat without frontend-design: expect a clear missing-foundation note and continued work, not silent installation or a blocked build. Compare baseline Sites, frontend-design alone, and the combined layer with the same brief and data.

For each run record: whether the skill was loaded without being named, chosen task pattern, selected park, structural choices visible in the output, unnecessary copy, task completion/errors, scope drift, and whether actual visual and behavioral checks occurred. Compare with a baseline build without the skill and record qualitative confusion without inventing benchmark thresholds. Improve instructions from demonstrated failures rather than adding speculative rules.
